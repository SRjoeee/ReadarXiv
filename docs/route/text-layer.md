# Selection and copy on a laid page: one transparent text layer per page (contract draft, web lane; engine lane to edit)

Status: DRAFT, edited by the engine lane 2026-10-23 (section 7 supersedes sections 2 and 3 where they differ). Owner's request (2026-10-23, via the coordinator): selection and copy on a laid page must work like a PDF viewer's. Today a laid page is a canvas copy + an SVG of the translated text (+ links): PDF.js's text layer is gone, so heading numbers, untranslated units, references and formulas cannot be selected, and a gesture cannot cross from translation into them. The visible paint (canvas + SVG) does not change. One PR after prefetch, one review; the engine view owns the layer's content, the host owns the page. Must not wait for OCG erasure (it only simplifies the "erased items" rule below).

## 1. What the layer is

One absolutely positioned DIV per laid page, above the SVG and below the links layer, built exactly as PDF.js builds the left pane's (`pdfjs.TextLayer`: one span per text item, `transform`/`scaleX` so the browser's selection rectangles match the drawn glyphs, `color: transparent`, `user-select: text`, `cursor: text`, spans in reading order). Its items are the union of:
1. **Kept original items**: the composed page's own text items (`page.getTextContent()` of the composed document's page: our content stream on a replaced page, the original's on an unchanged one) that are NOT erased by the removal plan (heading numbers, labels, untranslated units, references, captions the layer leaves, page numbers, anything outside the erase rectangles).
2. **Moved items**: the items of pieces the layer MOVES (a formula placeholder drawn as a crop at its drawn position: the crop's source rectangle's items are relocated by the crop's transform (dx, dy, scale) so the formula's text sits under its drawn ink).
3. **Translated items**: the translated text of each drawn unit, one item per word/token (or per run), at its drawn position and size (the door already returns the word table of the page: `words` tokens with l/r/y/h and the unit/sentence ids), transparent.
Reading order: by unit order (the paragraph's translated items stay contiguous and in the translation's order), kept items and moved items placed by their line's position among the units (top-to-bottom, columns by the layout's frames); crossing from a translated paragraph into the next heading number or reference is one continuous selection.
Copy yields the text of the selected spans (browser default): translated text as the translation, kept items as the original's text (the original's ToUnicode: a math glyph run may copy as the PDF's own text does).

## 2. Ownership (engine view; the removal plan decides)

An original text item is ERASED (not in the layer) iff the removal plan covers it: its bounding box's centre lies inside an erase rectangle of a unit the layer draws on this page (the same rectangles `removalOps` paints; for a delta page after OCG erasure: the items of hidden units). An item whose box straddles an erase rectangle's edge is erased when its centre is inside. Crop items are MOVED, not erased (rule 2). Items of units the layer does not draw (refused parts, no-layout pages, units kept as the original's) stay. Pure function of (page text items, erase rectangles, crops with transforms, drawn word table): `textLayerOf(items, plan, words)` in the engine view, unit-tested on synthetic pages. Pages shown as the original's (no layout, refused parts) get no layer of ours: the left pane's / the original page view's own PDF.js text layer is already there.

## 3. Division of work

- **Engine view** (public repo, `engine/view/*`, `layer-proto` door if needed): `textLayerOf` (the ownership/relocation/ordering above) producing plain data `{ items: [{ str, x, y, w, h, dir, fontSize, from: 'kept'|'moved'|'translated', unit?, word? }] }` per page, returned with the page (`pageOf` result beside `svg`, `words`, `links`) or computed by the layer side from the door's data + `getTextContent`; no DOM.
- **Host/page** (web `web/src/layer`, extension session): builds the DOM from the items with `pdfjs.TextLayer`'s own placement code (or a small equivalent using the same transform rules), attaches it to the page's `.axt-layer` wrapper between the SVG and the links, releases it with the page (retire/swap), sets `pointer-events` so the existing hover highlight keeps working (the highlight's hit test is geometric, not DOM-target based: verify), and `aria` (the text layer is real text: the SVG's text stays `aria-hidden`/non-selectable to avoid duplicate selection and duplicate screen-reader text; decide with the existing a11y audit).
- The SVG's translated text becomes `user-select: none` (selection comes from the text layer only, so there is one selectable copy of every piece of text).

## 4. Performance (first-class; measure before default-on)

Built after the page is committed (idle task, never on the lay/commit path: the page appears exactly as fast as today; the text layer a few ms later), only for pages near the view (retired with the page). Budget: <= 5 ms of main-thread time per page on the heaviest fixture page, <= 2000 DOM nodes per page (one span per item; merge adjacent items of a run into one span when their geometry is contiguous), no paint cost (transparent text; `contain: strict` on the layer). Report per page: ms, nodes, bytes of items; on 2602.23285v2 p8-p9 and 2610.10069v1 p4/p22 and a dense table page. The left pane's text layer is PDF.js's own and untouched.

## 5. Tests

Engine: `textLayerOf` on synthetic pages: items inside an erase rectangle dropped; outside kept; straddling by centre; crop items relocated by the crop transform; translated items at the word table's positions; reading order across a heading number, a translated paragraph, a reference; an unchanged/refused page yields no layer. Host: DOM from items (spans, transforms, order, `user-select`), released with the page, no layer on pages shown as the original's. E2E (real browser): select from a heading number through a translated paragraph into a reference with one drag: the selection text equals the expected string; Ctrl+C text; a formula's text selectable at its drawn position; the hover highlight still works over the text layer; a pixel test: the page screenshot is identical with and without the text layer (invisible); the a11y audit finds no duplicate text; Ctrl+F finds both translated and kept text. Perf gate: the section 4 numbers recorded.

## 6. Order and dependencies

After prefetch (one byte source, delta first). Independent of the pin except that the engine view change rides the next engine pin (public repo PR by the engine lane or the web lane's public-repo implementer: the engine lane decides who writes `textLayerOf`); after OCG erasure lands, rule 1's erase set becomes "items of hidden units" (the same function, different input). Open: **[Q1]** exact reading order for multi-column pages with floats (use the layout's frames; fall back to y-then-x within a column); **[Q2]** whether to merge translated tokens per line into one span (fewer nodes, coarser selection) or keep per-word spans (finer: the sentence highlight already uses words); **[Q3]** RTL/vertical items (not in v1: dir ltr only, items in other directions are kept as PDF.js gives them).

## 7. Engine lane's edit (2026-10-23): who writes it, where the data lives, the exact ownership rule

**(a) Who.** The engine lane writes `textLayerOf`. Everything it needs is engine-internal and already in hand where a page is laid (`layer-proto/run.mjs`): the page's text content (`tc`, read at ~2455 for the lay; from the draw's data on a prefetched page), the page's operations `ops` and `devOf`, the units with their rectangles and stream order, the crops (clip, source, transform) and the word table. A public-repo implementer outside the run would have to re-derive all of it. Host work (DOM, attach/release, aria, hover, perf of the DOM build) stays the web lane's.

**(b) Where it is returned.** Not derived by the layer side, and not on the commit path: a new door method beside `copyOf` and `unitAt`, `textOf(page)` -> `Promise<TextLayerData>` (plain data, fresh on every call, rejects like `copyOf` on a page not ready or after dispose), called by the host at idle after the page is committed. `LaidPage` stays as it is (svg, w, h, words, links), so the commit path costs nothing. If the run does not keep a ready page's text content and ops, `textOf` keeps a compact copy for pages the host may still ask for (items are `str, x, y, w, h`: ~100 KB on the heaviest page; evicted with the page); the first engine step measures that memory and, if it is too much, recomputes from a re-read of the composed page instead. Pure core: `textLayerOf({ items, styles }, plan, words)` in `layer-proto/textlayer.mjs` (unit-tested on synthetic pages), the door method only gathers its inputs.

**(c) Ownership rule, exact.** "Centre inside an erase rectangle" is not enough: the layer's drawing also has `paper` and `swap` rectangles that erase and `restore` operations that put the page's pixels back, in order. The rule is the one the links already use (`links.mjs` `erasedOf(ops)`): an original item is ERASED iff `erasedOf(ops)` is true at its box centre (device pixels, through `devOf`). One rule for ink, links and text. Then:
- erased and inside a crop's source rectangle (a placeholder drawn as a crop): MOVED, its box relocated by that crop's transform (dx, dy, scale), `from: 'moved'`; an item under a crop's source that is not erased stays where it is (kept);
- erased and in no crop: dropped (its translated text takes its place);
- not erased: kept as PDF.js gives it.
A page whose units are all kept as the original's (refused parts, no layout, `originalPageOf`) gets no layer from us; so does a page shown over arXiv's PDF. Over our own base page the items come from our compile's text content (marks are invisible, they add no text).

**Translated items (resolves Q2).** One item per DRAWN LINE of a unit, not per word: `str` the line's text, `x, y, w, h` its box, a per-line horizontal scale from the drawn width (the browser selects by character inside a span, as it does in PDF.js, whose spans are per text run). That keeps the node count to the number of lines (well under 2000) and the selection exact; the word table stays for the sentence highlight. `unit` carries the unit id; `word` is dropped from the contract (the first and last token index of the line may be added if the host's highlight wants them).

**Reading order (resolves Q1).** The unit order the links already use (`freezeLinks` ranks by the owner unit's stream index, then id); translated items of a unit are contiguous in the translation's line order. Kept and moved items belong to no unit: they are placed by their position in the page's frame order, y descending then x ascending within a column, columns by the layout's frames (fallback: the page's own text-content order for kept items). A moved item goes at its drawn position. A heading number (kept) therefore sits before its translated heading, a reference after the paragraph above it.

**Cost.** The engine's step is O(items x ops); it gets a work budget like the links' (`WORK_MAX`) and a grid over the erase rectangles; target <= 3 ms on the heaviest page (2602.23285v2 p8-p9) off the lay path; if the budget is spent the remaining items are kept (selectable duplicates are better than lost text, and invisible). Host DOM build stays within the section 4 budget.

**Q3** accepted as written (ltr only; other directions kept as PDF.js gives them).

**Order.** One engine PR (textlayer.mjs, `textOf` on the door and its d.mts, tests per section 5's engine list, a perf record), after prefetch ships and after the PRs now in flight; the coordinator ranks it against the engine queue (#436, then the layer fit for stretched lines, the revtex4-2 and cite.sty marks, the audit's root 1). The web lane's host PR follows the engine PR (it can start against the synthetic data shape in section 3 as soon as the type is agreed: `{ items: [{ str, x, y, w, h, dir, fontSize, from: 'kept'|'moved'|'translated', unit? }], page: { w, h } }`, PDF units of the page, y up, unrotated, as `LinkRecord.boxes`).
