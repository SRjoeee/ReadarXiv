# Our base as a PDF incremental update over arXiv's original ("the delta"): contract (web lane draft for the pipeline lane to edit)

Status: DRAFT, nothing implemented. Direction from the owner (via the coordinator, 2026-10-23): the alias table is a patch on "two documents"; the long-term form is ONE document: arXiv's original bytes + a small delta + the remover's tails. This note is the contract between the pipeline lane (builds the delta at prepare, in the box) and the web lane (container wiring, Worker storage, reader/extension transport). Edit in place; open questions are marked **[Q]**.

## 1. What changes, in one picture

Today (BUNDLE 8, #67): composed document = OUR base (a whole PDF, 28 MB on 2602.23285v2, read from /base/) + tails; the left pane reads arXiv's PDF from /orig/. Two documents, two byte streams (the p8 stall: 16.6 MB of identical images read twice).

Delta form: composed document = `orig.bytes` (arXiv's PDF, byte for byte, the SAME ranged source and chunk store the left pane already uses) ++ `delta` (a PDF incremental-update section, small) ++ `tail_1 .. tail_n` (the remover's sections, as today). Byte map of the composed document (PDF.js sees one file):

    [0 , O)            arXiv's PDF, O = head.orig.bytes          (ranged, shared with the left pane)
    [O , O+D)          delta section                             (D = head.base.delta.bytes; in memory, a bundle object)
    [O+D , ...)        tails (remover), each /Prev-chained        (in memory, as today)

The delta is an ordinary incremental update: its objects, one xref section (table or stream, whichever the original uses: a mixed file is not allowed) and a trailer with `/Prev` = the original's startxref, `/Size` raised, `/Root` the original's. Its `startxref` (absolute offset in the composed coordinates) is `head.base.xref`; the first tail's `/Prev` points at it (the existing chain rule, layout/chain.mjs). The pages the delta does not replace are the original's, untouched.

## 2. What the delta contains

For every page `p` that the layer draws (a page of a part that HAS a layout; a page covered only by layoutless parts is never replaced: see 5):

1. **The page object replaced**, same object number and generation as the original's page object `p`, a new body: every key of the original's page dict kept verbatim EXCEPT `/Contents` and `/Resources`, which are ours (below); `/Parent`, `/MediaBox`, `/CropBox`, `/Rotate`, `/Annots`, `/Group`, `/StructParents`... stay the original's (see **[Q1]** for `/Annots`).
2. **`/Contents`**: our page's content stream(s) as NEW objects (stream bytes copied verbatim from our final-pass PDF, same filter; never re-encoded). One object per our content stream, in order.
3. **`/Resources`**: a NEW resources dict (or direct dict in the page) built from OUR page's resources, every entry mapped to an object the composed document will hold: for each resource (Font, XObject (Image and Form), ExtGState, ColorSpace, Pattern, Shading, Properties, ProcSet) of our page: if an identical object exists in the original (section 3) the entry is that object's number (`/F12 31 0 R` where object 31 is the original's, even though our content stream calls it F12 and the original called it F3: names live only in the page's resources, so no content stream is rewritten); else the entry is a NEW object in the delta (copied closure, section 3).
4. The **new objects** (content streams, resources not found in the original, the closures of those) numbered from the original's `/Size` upward, in the delta's xref.
5. NOTHING else: the catalog, page tree, outlines, names tree, named destinations, page labels, the original's annotations and its info dict stay the original's. Our compile's catalog/names/outlines are not carried.

The tails (remover) then edit the composed document's pages as today: they replace page objects again by number (adding the erase overlay etc.), chained /Prev to the delta.

## 3. Resource identity: exact bytes + dict, by a canonical form

Two objects are the same resource iff their **canonical form** is equal. Canonical form of an object O (computed identically for the original's objects and ours, one pass each, memoised):

- a stream: `canon(dict) ++ sha256(decoded? NO: the stream's raw bytes as stored, i.e. with its filter)`. Raw stored bytes: no decoding, no re-encoding (equality of what is on disk). The dict is canonicalised with `/Length` removed.
- a dict/array/name/number/string: a deterministic serialisation (keys sorted; numbers in their shortest form; strings by decoded bytes; names by decoded bytes; inline whitespace and comment irrelevant) in which every indirect reference `n g R` is replaced by the canonical-form hash of the referenced object (a Merkle graph). Reference cycles (parent links like `/Parent`, `/P`) are cut: such keys are excluded from the form (a resource closure has none in practice: fonts, images, forms, ExtGState, colour spaces); an unexpected cycle = the object is "unmatched" (included in the delta), never an error.
- Equal Merkle hash => reuse the original's object number; the closure of a matched object is never copied (it is already there). A resource matched at the top reuses its whole sub-graph (font dict, descriptor, font file, ToUnicode, widths).
- **Fonts**: matched by the above (so a pdfTeX subset font equals arXiv's only if the dict, descriptor, FontFile stream and ToUnicode are byte-identical: expected when both compiles are pdfTeX of the same TeX Live year; not expected for dvips vs dvipdfmx `latex` papers: those fonts are included). **Images**: stream bytes + dict + SMask/ColorSpace closure. **Forms (Type /XObject /Form)**: stream + dict (+ its resources: Merkle).
- **Partial identity is not identity**: a font with the same name and a different subset is a different object: included whole. No glyph-level merging.
- The decision is a pure function of the two files' bytes: the same inputs give the same delta bytes (no timestamps, no random ids), so the delta is content-addressed and reproducible.

What the delta never does: modify an original object's bytes (it replaces objects by appending new versions), re-encode a stream, drop or reorder the original's content outside the replaced pages.

## 4. Which pages are replaced

Page `p` is replaced iff (a) the layer draws on it: some part with a layout holds it (the same predicate as the reader's `noLayoutPage`, by pages or reach) AND (b) our page's content differs from the original's: `canon(our contents ++ our resources)` != `canon(original contents ++ original resources)` (so a page whose compile output equals arXiv's byte for byte costs nothing). Pages of refused parts, and pages no layout holds, are the original's by construction (this deletes the "show the original's page" special case in the reader for them: the composed page IS the original's page: the reader's `noLayoutPage` rule stays only as the do-not-ask-the-door rule).

Page count and every page box must still be equal (the existing check; the delta keeps the original's `/MediaBox`, so a size mismatch would misplace our content: fallback `boxes` as today).

## 5. Head and catalog fields (proposal; names are the pipeline lane's call)

`head.base` for source `ours` gains `kind`:
- `kind: 'delta'`: `{ source: 'ours', kind: 'delta', bytes: D, sha256: <sha256 of the delta section>, xref: <startxref offset of the delta section in COMPOSED coordinates = O + (offset inside the delta)>, over: { bytes: O, sha256: <orig sha256> } (must equal head.orig), pages, boxes?, check, tree, stats: { replaced: <pages>, reused: { fonts, images, forms, other }, included: { bytes, objects } } }`. The delta bytes are a **bundle object** (content-addressed under the CTAG like the units chunks, with its own suffix: `o/<sha256>.delta`, the engine's `deltaKey`; the catalog names it: `base: { source: 'ours', kind: 'delta', object: { key, sha256, bytes } }`), NOT a /base/ PDF: no new route, no `base/` R2 key for this kind.
- `kind: 'full'` (today's whole-PDF base: `/base/` object): kept only as a FALLBACK mode (section 7); same head fields as today.
`orig` stays as today ({bytes, sha256}). `layerDraws(base)` stays true for source 'ours' of either kind.

## 6. The reader's change (web and extension): small

1. The composed document's byte source is the ORIGINAL's `rangeSource` (the one the left pane opened, same store, same bound: Content-Range total == head.orig.bytes, the first answer's strong tag, and now the catalog's `base-etag` for the original comes back for delta heads: the layer is bound to R2's original as in BUNDLE 4-7), followed by an in-memory segment list: `[delta bytes, ...tails]`. Today's mechanism is `composedRange(source, total, tail, begin, end)`: a range spanning the seam between the source and the tail is split. The delta is just a longer `tail` (delta ++ tails concatenated in memory), with `total = O`: **zero change to `composedRange` itself**; what changes is only (a) which URL/source `composed()` opens (the original's, not `/base/`), (b) where the in-memory tail's first bytes come from (the delta object, fetched like any bundle object by digest, + the parts' tails), (c) the bound (the original's). The `/base/` routes, the base store, `bindOurs`' 'ours' meaning in the extension (the left stays the tab's PDF; its composed document is arXiv's bytes: the old `endsAlike`/`sha256Of` proof applies again: the tab's PDF vs head.orig) all become the `kind: 'full'` fallback path only.
2. The page copy rule (`drawnSource`): for a page the delta does NOT replace the composed page is byte-identical to the left's, so the left canvas is a valid copy source again (the pre-route shortcut, free); for a replaced page the copy is rendered from the composed document (as now). The head's `stats` / a replaced-pages list tells which: **[Q2]** do we want `base.replaced: [page,...]` in the head (compact ranges), or let the reader ask `doc.getPage` and compare content refs? Recommendation: ranges list in the head (cheap, exact).
3. Request ordering and the alias table are not needed: one byte source.
4. PAGE_MS, prefetch: unchanged, separate.

## 7. Fallback ladder

1. `delta` built, checks pass (same pages/boxes/carry as today): head `kind:'delta'`.
2. The delta builder cannot (an original it cannot parse safely: encrypted, a structure the writer does not handle, a resource graph over a bound (delta bytes > 24 MiB, objects > 200k), or the delta fails its own proof, see 8): fall back to `kind:'full'` (today's whole base, stored at /base/), with a `why` stat `delta-<code>`.
3. Everything else as today: `source:'arxiv'` + why => arXiv's PDF untranslated.
Heads are written once; a paper whose delta later turns out wrong is re-prepared (the versions bump), never patched.

## 8. The prepare-time proof (the pipeline lane builds and checks it before the head is written)

Build the delta from (`orig` bytes, our final-pass PDF bytes, the layout's replaced-page set); then, in the box, with the engine's PDF.js: (1) open `orig ++ delta` and check page count, boxes, and for each replaced page that PDF.js's rendering of the composed page equals its rendering of OUR page (pixel-exact where our compile is deterministic; the same measure as phase 1's pixel test), for each unreplaced page that it equals the original's; (2) the resources of every replaced page resolve (no missing object, no cycle); (3) the xref section parses and `/Prev` points at the original's startxref; (4) size bounds. Any failure => ladder step 2. The proof's counts go in `stats`.

## 9. Worker and container (web lane)

- Container prepare child: after the final pass, call the engine's `deltaOf(origBytes, finalPdfBytes, replaced)` (pure; the pipeline lane's), pass `ours.delta` to `layerOfPaper` (head `kind:'delta'`), announce the delta as a LAYER OBJECT (role as the units chunks/parts: content-addressed under the CTAG), not as a base PDF (PR 3's `base` role/`/base/` store remain for `kind:'full'`). The service re-checks it (size, digest, xref coherent with `head.base.xref`, the original it extends = the run's `orig`).
- Worker: commits the delta object like other layer objects (checked put under the CTAG key), BEFORE the head; the head commit binds a delta head to R2's `orig/` by length+sha256 as the BUNDLE 4-7 `arxiv` binding did (baseBinding over orig, `base-etag` back on head/parts/catalog) and requires the delta object present with its digest; a `full` head binds as in PR 3.
- Remover: tails continue the delta's xref (`head.base.xref`), reading `orig ++ delta` as its base document (PR 3's remover copy: it already builds from a checked file: here the file is orig bytes + the delta object).
- Reader/extension: section 6.

## 10. Measurements before building (pipeline lane, read-only, on the gate pack + 2602.23285v2 + two `latex` papers)

Go/no-go: median delta < 10 % of the original; worst case < 24 MiB; proof passes on all.

## 13. Pipeline lane review and first numbers (2026-10-23)

**Stream-level measurement (done, read-only; scripts delta/streams.mjs, delta/measure.mjs; table in delta-measure.md).** Every indirect stream of arXiv's PDF and of our base, matched by (length, SHA-256) of the raw stored data, on the gate pack's 7 papers and the p8 pair:
fonts byte-identical in 7 of 8 papers (all of them in 5; 1512.03385 15/27, 2307.16209 17/22, 2609.26457 44/47), images identical in EVERY paper that has any (2602.23285: 60/60, 26.1 MB; 2608.16117: 81/81, 44.4 MB), page content streams ("other") mostly identical (1706.03762 58/73, 2608.04322 424/437). Upper bound of a delta (base bytes minus identical streams, so it still counts every non-stream object, the object streams and the xref that a real delta rewrites or drops): 1% of the base on the two heavy-image papers (0.21 of 43.9 MB, 0.18 of 26.8 MB), 12 to 47% on the light ones (a base of 0.7 to 3 MB). A tighter estimate from the non-identical streams alone: 0.3% (2608.16117, 2602.23285), 5% (2608.04322), 10-11% (1706, 1810), 19-28% (2307, 1512, 2609). Caveat: the pack's bases were built on one tree per paper (the pack's, not the banner's); the staging bases (banner routing) should match more, to be measured after the sweep. latex (dvipdfmx vs dvips), xelatex and lualatex papers will match little (fonts and images are re-encoded by another driver): the delta then approaches the base and `kind:'full'` is the right fallback.

**A real builder is being spiked now** (throwaway, outside the repo, an Opus agent): canonical Merkle over @cantoo/pdf-lib objects, replaced pages, resource remapping, the delta section with the original's xref kind, and the section 8 proof (PDF.js opens the composed bytes; text equality; pixel equality on a sample). **Edits and answers**
1. **Go/no-go metric.** "Median delta < 10% of the original" over-weights light papers (a 0.7 MB original with a 0.2 MB delta is 28% and irrelevant in absolute terms) and hides the heavy case that motivated this (2602.23285: 26.8 MB). Proposal: (a) total delta bytes / total original bytes over the sample < 10%; (b) per paper delta <= max(10% of the original, 512 KiB); (c) worst case < 24 MiB; (d) proof passes on all. Decide after the spike.
2. **Q3 (xref style): yes, reuse.** remove.mjs already writes its update "with a cross-reference section of the original's kind with /Prev" (isStream test on the original's last section, table or /Type /XRef stream, /W [1 4 2]); the delta writer should share that code (extract a small `appendSection({orig, objects, prev, size, root...})` in layout/), and tail.mjs `tailLinks` already reads both kinds. The remover's add-on APPENDS pages after the document's own (set R at N+p, page-tree root rewritten): unchanged by the delta, it simply starts from `head.base.xref` (the delta's section) instead of the original's.
3. **Head fields.** `base.over` duplicates `head.orig` (already required on ours): drop `over`; require `orig` on a delta head and `base.kind: 'delta'`. `base.bytes`/`sha256` = the delta section's; `xref` = its startxref in composed coordinates (so the tail chain rule `c.xref >= composed length` in remove.mjs holds). `base.replaced`: ascending, non-overlapping page ranges `[[from,to],...]`, bounded (at most 4096), as the replaced-pages list Q2 decided; `stats` bounded, exactKeys, only counts. BUNDLE: no bump (8 is unreleased); heads without `kind` are 'full'.
4. **Proof (section 8) should be structural first, pixels in the lab.** In the box, rendering both pages for every replaced page costs seconds per image page; the same assurance comes cheaper from (i) a second, independent parse of the COMPOSED bytes by the object layer: canon(composed page graph) == canon(our final-pass page graph) for every replaced page, and unreplaced pages' canon equal the original's (exact, linear in the delta); (ii) PDF.js opens the composed document with no xref warning, page count and every box equal, and each replaced page's text content (strings, positions, 0.01) equals ours; (iii) `/Prev` == the original's startxref and the new `startxref` points at the section. Pixel equality stays a lab gate on the pack (and the spike's evidence), not a prepare-time step.
5. **Memory/time in the box.** pdf-lib parses the whole original: on a 46 MB original expect a few hundred MiB transient; the maker stage already peaks at 426-468 MiB of the child's 768 MiB. Build the delta after the page pass has released the maker's documents (or in the remover's child), and give the builder its own HELD/BYTES bounds as remove.mjs does (HELD_MAX, BYTES_MAX); over a bound: `kind:'full'` with a `delta-bound` why.
6. **Writer and engine API.** Pure `deltaOf(origBytes, finalBytes, { replacedPages })` in the engine (host-called like creationEpochOf; the page pass receives the finished delta in `ours.delta` and writes it into the head, validating shape and bounds in readHead); the same function is what the lab spike prototypes.
7. **Risks not yet in the contract.** Tagged originals (/StructParents, marked content) when the original page is replaced; /Annots kept from the original with our content (Q1 accepted); pikepdf-rewritten 2026 originals carry arXiv's stamp on page 1, which our page lacks: page 1 is replaced (consistent with the owner's "no stamp on the right"); an original with an encryption dictionary, a hybrid xref, or an unparseable object: fallback `full`; a replaced page object that lives in an object stream of the original (an uncompressed override with a type-1 xref entry, fine in PDF 1.5); pdfTeX's /Group or /PieceInfo keys of a page the original and ours disagree on (kept from the original).

## 14. Head shape fixed (pipeline lane, confirmed by the web lane, 2026-10-23)
`base.kind` is `'delta'` | `'full'` (a head without `kind` reads as `full`). `base.replaced` = `[[from,to],...]`, 1-based inclusive page numbers, ascending, non-overlapping, adjacent merged, each within [1, pages], at most 4096 ranges; only on `kind:'delta'`, absent on `full`. `base.stats` for a delta head: integers only, exactKeys: `{ replaced, reused: { fonts, images, forms, other }, included: { bytes, objects } }`. A delta head requires `orig` (no `over`). The delta is built at the END of the maker child, after the maker has released its documents (it holds handoff-base.pdf and orig.pdf and the delta must come from the same final PDF the maker read); the pipeline lane confirms with the spike's memory numbers on 46 MB originals. The engine's structural proof includes PDF.js opening orig++delta and extracting the same text as our page for every replaced page.

## 14. GO (coordinator, 2026-10-23) and the build requirements from the spike

**Decision.** The delta is GO. Accepted rule: total delta / total originals < 10% (measured 2.48% on 8 pairs), worst case < 24 MiB (measured 0.70 MiB), per paper delta <= 35% of the full base (measured worst 30%; replaces "max(10%, 512 KiB)" and the median), and the section 8 proof passes (it did on 8/8: PDF.js opens orig ++ delta without a warning, page count and boxes equal ours, text and operator lists equal ours on 302/302 replaced pages, xref exact, /Prev = the original's startxref, pixels 0 on 35 sampled pages). Order: items 1, 2 and 4 of the sweep findings first, then ONE engine/box PR (pipeline lane) and ONE web PR (web lane), one pin. Spike: docs/route/delta/spike/ (delta.mjs, build.mjs, prove.mjs, pixels.mjs; out/summary.md).

**Page equality modulo the marks (follow-up run, result to be added).** Our laid pages differ from arXiv's only by the `/axt-... ri` mark operators in the content stream (no-ops the engine reads at prepare). A page whose decoded content, after removing exactly those operators, equals the original's decoded content AND whose resource closure is canonically equal to the original's is UNCHANGED: nothing is written for it. A replaced page copies our content stream verbatim, marks included (no re-encoding: proven pixel-exact). `base.replaced` then lists the pages that really differ (also the input of the per-unit in-place check), not the laid pages. §4(b) holds as written, but "equal" is modulo marks.

**Build requirements (from the spike; the engine/box PR must meet them)**
1. Stream bytes by the RESOLVED /Length (follow an indirect /Length), as PDF.js does; never take pdf-lib's scanned `endstream` boundary: it eats a trailing CR/LF (1810.04805v2: 6 image streams read one byte short). Matching by (resolved length, SHA-256 of the exact stored bytes); a builder that copies such a stream must copy exactly the resolved length.
2. The in-box proof (structural, section 8) must (a) capture `console.warn` from PDF.js (it reports xref trouble there, not through exceptions), (b) check EVERY xref entry of the delta points exactly at its `n g obj` (PDF.js forgives an offset shifted onto whitespace and rebuilds a broken xref while still reporting the right page count), (c) `/Prev` equals the original's startxref and the new startxref points at the section, (d) text equality per replaced page against our final PDF, plus operator-list equality when the cost allows (the spike measured text alone is NOT discriminating: text equals the original's on pages that differ).
3. The PIXEL proof is a lab gate, not a prepare step: PDF.js in Chromium is not deterministic on some pages (1810.04805v2 pages 3 and 15 rendered 8-48 pixels apart on 1 of 12 renders of OUR page alone; 0 in 22 with `isImageDecoderSupported:false`): any pixel gate re-renders on a mismatch and runs with that option.
4. chain.mjs / remove.mjs: the delta is the BASE of the tails: committed end = O + D, `xref` = `head.base.xref` (the delta's startxref in composed coordinates), next object number = the delta's /Size (with an xref stream the /Size includes the stream's own number, so the remover's largestObjectNumber + 1 stays consistent); `tailLinks`' `root`/`first` (least object numbers) mean nothing for the delta; TAIL_CAP (1 MiB per part's tail) does NOT apply to the delta (2307.16209v1's is 0.70 MiB): it applies to the remover's parts only. Extract the incremental-section writer from `makeAddon` into a shared `appendSection` (xref of the original's kind: table or stream, /W [1 4 2], runs grouped into subsections / /Index pairs).
5. The reader hides the composed document's link layer on replaced pages: the original's annotations are kept (Q1) but only 90.9% of the original's link rectangles match ours on the thesis (37 of 147 pages differ), and the layer draws its own links from the layout; the reader must check there are no double links. Named destinations: our base carries ~10x the named destinations (the `axt-` marks); the delta drops them; nothing reads them from the composed document (base.mjs reads the marks from our final pass, reader-view follow() resolves link names on the LEFT document).
6. Objects are written uncompressed (they barely compress: the delta is mostly Flate streams); numbers grouped into runs.
7. Original xref kinds seen: table (old, with orphan object streams: type-1 entries of the delta override, PDF.js and pdf-lib alike) and stream (pikepdf 2026: page dicts as type-2 entries in object streams, overridden by type-1). Page 1 of every original has /Contents as an ARRAY (the arXiv stamp): page 1 is replaced (no stamp on the right, as decided). Not measurable in the spike and to be covered in the PR's tests: a linearized original (PDF.js's linearization check throws when /L differs and loads normally, as for the existing tails), a `latex` (dvipdfmx vs dvips) paper (expected little matched: `kind:'full'` fallback when delta > 35% of the full base).
8. Memory: the build is cheap (51-208 ms, 93-363 MB peak on a 46 MB original); the expensive part is the proof (1.2-3.5 s, up to 1.1 GB in Node, three documents' operator lists): do the structural proof without operator lists in the box (xref, /Prev, text per replaced page, graph canonical equality of the composed pages), operator lists in the lab.

## 15. Result of the modulo-marks run (spike follow-up, 2026-10-23): page equality modulo marks does NOT hold

Predicate tested: our decoded content, after removing exactly the mark operators (`/axt<name> ri` + whitespace, count equal to PDF.js's setRenderingIntent ops for axt names on every page), equals the original's decoded content, and our resources are canonically equal. Result on the 8 pairs: **4 of 302 pages unchanged** (2602.23285v2 pp12-14, 2608.04322v1 p13); the replaced list is the laid pages (298); median delta/original 12.13% -> 12.02%, total 2.484% -> 2.467%, worst 0.70 MiB unchanged; build time and memory unchanged; the proof passes on the new composed documents (the 4 unchanged pages equal the original's and, modulo marks, ours).
Cause: each mark is a `\pdfliteral` in text mode, so pdfTeX closes and reopens the TJ array at every mark, splits strings (`(\051)(.)` vs `(\051.)`), changes whitespace (`]TJ\n/F84` vs `]TJ/F84`) and re-expresses positioning: the content streams differ structurally, not only by the marks. Resources differ too on 266 pages (mostly pdfTeX's font numbering).
Consequences: (1) `base.replaced` = the laid pages for this design; the reader's copy-source shortcut for unchanged pages applies only to pages the layer does not lay. (2) Visually the pages are mostly the same: 99 of 302 are PIXEL-identical to arXiv's (5/15, 32/40, 15/19, 31/147, 12/13 on the five papers whose tree matches best; 0 on 1512.03385v1 and 2609.26457v1; page 1 never: the stamp), so a stricter "our page equals arXiv's" signal exists but not at byte level. (3) The one lever: a base pass WITHOUT the `ri` literals (the unmarked compile, marks read from the marked one and mapped by glyph sequence; on 2608.04322v1 every page matches arXiv's once whitespace and TJ splits are normalised). It costs a compile and a mapping, shrinks the delta by the content share only (50-500 KB per paper), and its real value would be the layer drawing over a page that IS arXiv's wherever the tree matches: not part of this delta PR; noted as a later lever, to decide on measurements of how many sweep papers would gain.
Not changed: GO and the accepted rule (section 14); the build requirements of section 14 stand; the "replaced pages" list stays the laid pages.

**Rejected (2026-10-24): our pages as a second page run in one document** (arXiv's N pages untouched and ours after them, both panes one PDF.js document): PDF.js 6.3.289's GlobalImageCache shares only 10 of 2602.23285v2 p8's 20 images (it stops caching at 10 images holding 50 MB), and one worker serialises both panes' decode where two documents decode in two workers in parallel. Numbers in the spike report (route/spike-one-doc/report.md, scratch).

## 16. Prefetch ("预读", owner's decision 2026-10-23): contract and plan (web lane; one PR after the delta web PR, one review)

**Decision.** When idle (after the visible pages are painted), the reader prefetches the bytes of the next 1-2 pages so a heavy page is ready before it scrolls into view. The owner's rules: lowest priority; cancelled when the viewport jumps; bounded by a byte budget per idle window; counted in analytics as `prefetch`, not as a visit. Reading order stays: (0) the visible pages' ORIGINAL bytes, (1) the layer's needs, (2) prefetch.

**Why it composes with the delta.** After the delta there is ONE byte source for both panes (the original's ranged source and its chunk store, `originalStore`, 64 MiB LRU; the composed document's replaced pages point at the original's resource objects, the delta/tails are in memory). Prefetching the ORIGINAL's page bytes therefore warms both panes at once: the left pane's next page and the composed document's. (Without the delta two documents would need two prefetches: another reason the delta comes first.)

**1. A priority gate in the shared byte source** (the `rangeSource` the original's documents read through; web/src/ranges.ts and the extension's session/ranges.ts): every range read is tagged by its document with a class: `visible` (the left pane's document), `layer` (the composed document), `prefetch` (the prefetch document, below). Start rule: a read of class k starts only when no read of a class below k is in flight (`visible` < `layer` < `prefetch`); `layer` reads wait at most LAYER_YIELD_MS = 15 000 per read (no starvation); `prefetch` reads never wait out: they stay queued/aborted (below). A read already in flight is never cancelled except a prefetch read by the viewport rule. In-flight accounting by try/finally (no leaks on error/abort); zero added latency when nothing of a lower class is in flight. Cache hits (the chunk store) are served at once in every class.

**2. The prefetch document.** A third PDF.js document of the ORIGINAL, opened lazily on the first idle window through a `rangeSource` wrapper of class `prefetch` (same store, same bound/tag as the left's), used only to run `getPage(n).getOperatorList({ intent: 'display' })` for the target pages (PDF.js's own way to ask exactly the ranges a page needs: content, fonts, images; the bytes land in the shared store; the operator list itself is discarded; image decoding CPU happens in its worker: measure, see 6). It is destroyed (task `destroy()` + the wrapper's AbortController aborted) when the viewport jumps, on `visibilitychange` hidden, and with the paper. Why a separate document: tagging and cancelling are then exact (every read through it is prefetch; aborting it cancels only prefetch reads); prefetching through the left document would mix its demands with prefetch reads and could not be cancelled.

**3. When it runs (idle).** The visible pages of the left pane are painted (`pagerendered` for each page in view, the viewer's `updateviewarea` settled), the layer side's queue for the visible pages is empty (laid or the original shown), no scroll/zoom/resize for IDLE_MS = 600, the tab visible, `navigator.connection.saveData` false and `effectiveType` not `slow-2g`/`2g` where present, and `requestIdleCallback` fired. Target: n+1, then n+2 where n = the highest visible page (forward only; backward is not prefetched); one page at a time; the second starts only when the first completed AND the window's budget remains. Never beyond page count.

**4. Budget and cancellation.** BYTES_PER_WINDOW = 32 MiB of prefetch bytes completed per idle window (a window = one continuous idle period; a new window after a viewport change settles); a page whose first read would exceed the remaining budget is not started (a heavy 16.6 MB page fits, 2 of them do not: the second waits for the next idle window). Total ahead of the viewport is bounded by 2 pages by construction. Viewport jump (the visible page set changes to one that does not include n..n+2's predecessors: any scroll that changes the highest visible page, zoom, resize, display-mode change) => abort in-flight prefetch reads and destroy the prefetch document at once; the chunk store keeps what completed. Fully idle for a page => nothing queued. The prefetch never starts while a `visible`/`layer` read is in flight (the gate).

**5. Analytics (not a visit).** A visit is the paper's open (`POST /api/open`, counted by Admission and the events); prefetch makes no open. The Worker counts prefetch separately: prefetch range reads carry `x-axt-purpose: prefetch` (same-origin /orig/ reads on the site; for the extension's cross-origin /api/v1/original reads the header must be allowed by the route's CORS (`access-control-allow-headers`, with `access-control-max-age` 86400 so the preflight is once a day)); the Worker's read route (read.ts `serve`, layer-api.ts originalRead) writes ONE analytics point per prefetched RANGE REQUEST... if that volume is too high, an aggregate: the reader sends one `POST`-less beacon per window? **[decision at the PR: header + a counter event `prefetch` with blobs {kind:'prefetch', end: 'range'} and doubles {bytes}; never anything of the visitor/paper (the privacy rule at the top of metrics.ts)]**. Prefetch traffic is excluded from visitor stats by construction (no open event), and tester traffic keeps its tag.

**6. Measurement before enabling by default (staging, 2602.23285v2 p7->p8 and a light paper):** time to first paint of p8 with and without prefetch on a throttled link (1.5 MB/s), the bytes prefetched but never used (jump away), the CPU of the prefetch document's operator list on the heavy page (main-thread long frames must not appear: its work is in the worker), memory (store occupancy, third document). Gate: no regression of the visible page's latency (the gate keeps prefetch below), the p8 stall's wait drops to ~0 after a idle window on page 7, wasted bytes <= 50 % of prefetched on random jumps.

**7. Scope and tests.** Web: web/src/ranges.ts (gate + wrapper), the session/viewer hooks for idleness (web/src/session/run.mjs, the viewer events), analytics in the Worker; public repo: the extension's session/ranges.ts + run.ts (same gate/prefetch), the shared view's idle hooks if the viewer events live there. Tests (fake clock, fake source): the gate's three classes and bounds, idle detection, target pages and forward-only, budget (second heavy page waits for the next window), abort on jump leaves the store intact and leaks no in-flight count, saveData/hidden tab off, the header on prefetch reads only, the Worker counts the purpose header and writes no visitor data; e2e: scroll to page 7, idle, the /orig/ requests for page 8's streams appear before any scroll to 8 and carry the header; a jump aborts them; no prefetch while pages are still painting.

## 17. Box time at the pin 699b4aea: what the prepare's time is made of (box-time owner, 2026-10-24)

The question: a new paper's prepare (the box: probe, compile, left, maker) took a median 31 s on staging on 2026-10-23
(LAYOUT 16, the pin 699b4aea) against the route's 16 s. Read from staging's job records of 2026-10-21 (LAYOUT 11, 2 compiles),
2026-10-22 (LAYOUT 12, our final pass added) and 2026-10-23 (LAYOUT 16), each paper paired with itself; the box time is the

**Most of it is the boxes, not the work.** Staging runs on two kinds of CPU (the record's `child.cpu.digest`): `a0575d…`, whose
